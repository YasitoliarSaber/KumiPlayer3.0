# KumiPlayer 前端重构 · 设计输入

本目录是给**产品设计方（OpenDesign）**使用的输入资料，唯一用途是让设计方在不了解代码实现的前提下，准确理解 KumiPlayer 这个产品需要重新设计成什么样。

## 1. 这个目录和工程资料的区别

KumiPlayer 的前端重构在动手前先做了一次完整的系统事实梳理，产出的是**工程层资料**（记录在仓库的 `docs/current/` 下）：包含接口清单、数据结构、导入链路、测试状态、代码位置等内容。

那套资料面向**实现者**，不是设计输入。本目录是它的**提炼结果**：

| 工程层资料（不进设计输入） | 本目录的处理方式 |
|---|---|
| 接口清单与请求 / 响应字段 | 只保留"前端能获得哪些能力"，不出现任何接口 |
| 数据结构与表设计 | 只保留"数据里有什么概念"（作品 / 季 / 集 / 版本 / 图片 / 进度） |
| 代码位置与文件行数 | 完全移除 |
| 导入链路的技术步骤 | 转写为"用户看到什么、等多久、失败怎么办" |
| 测试结果与构建命令 | 完全移除（当前工程状态另见本目录 `rebuild-baseline.md`） |

## 2. 阅读顺序

| 顺序 | 文件 | 解决什么问题 |
|---|---|---|
| 1 | `product-overview.md` | 这是什么产品、给谁用、核心体验是什么、明确不是什么 |
| 2 | `feature-map.md` | 产品有哪些功能、每个功能对用户的价值、哪些需要界面 |
| 3 | `page-requirements.md` | 需要设计哪些页面、每页要让用户看到什么、能做什么 |
| 4 | `user-flow.md` | 用户会按什么顺序使用、每一步在等什么、出错回到哪里 |
| 5 | `backend-capability-summary.md` | 前端能拿到哪些能力（不需要知道实现方式） |
| 6 | `design-constraints.md` | 设计时不能突破的边界、不能凭空增加的功能 |
| 7 | `rebuild-baseline.md` | 本次重构的范围与当前的工程状态（给协调者看，不是设计素材） |

## 3. 使用要求

- 设计必须严格基于本目录描述的能力。本目录未提到的功能，视为产品中不存在。
- 本目录**不提供任何视觉方案**：布局、信息层级、控件形态、动效、视觉风格全部由设计方决定。
- 现有前端界面**不作为设计起点**：它会被完全替换。设计方不需要、也不应该去参考它。
- **不要读取同仓库 `docs/current/` 下的工程层资料。** 本目录中出现的路径引用只是给协调者看的来源说明；设计方的唯一依据是本目录。工程层资料包含接口、数据结构与测试细节，对设计是噪音，也可能诱导设计越界。
- 如果某个设计想法需要产品新增能力，请单独列为"需要产品变更的提案"，不要混入主设计方案。

## 4. 维护约定

- 本目录只从 `docs/current/` 提炼，不引入新事实；两者冲突时以 `docs/current/` 及其上游源码为准。
- 产品能力发生变化时，先更新 `docs/current/`，再同步本目录。
